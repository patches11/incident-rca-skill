# Reflection

> If you had to deploy this tomorrow for 20 engineers and trust the code it helps produce in production, what would you change?

The short version: I would deploy it **tomorrow as an advisor in shadow mode**, not as something anyone acts on yet. The read-only design means the deployment risk is low; the risk that matters is a confident, wrong RCA that a tired engineer believes at 3am. Everything below is aimed at measuring and shrinking that risk.

## Before day one

1. **Shadow mode first.** The skill runs on every page, in parallel with the human on-call. Its report goes to a private channel, not the incident channel. After each incident, the on-call marks it *correct / partially correct / wrong / abstained correctly*. Nobody relies on it until there are ~30 labelled incidents and a measured accuracy per incident class.
2. **Replace synthetic scenarios with replays of real incidents.** My six scenarios are generated by me, so they share my blind spots, and the fixtures are cleaner than real telemetry. The eval set should come from the org's last 6–12 months of postmortems: snapshot the telemetry windows, write `ground_truth.yaml` from the postmortem, and run the skill against it. Every new postmortem adds a case. Then the pass rate means something about *this* org.
3. **Scoped, audited credentials.** One read-only service account per environment, with access only to metrics/logs/deploy history. No prod database or cloud-console credentials anywhere in the agent's environment. The server already writes a per-investigation audit log of every query; ship that to the normal audit pipeline. The Claude Code harness should run with a deny-list (`kubectl`, `psql`, cloud CLIs, `git push`) as in the eval settings, enforced by managed settings rather than per-user config.
4. **Stronger redaction.** The regex redactor is a floor, not a guarantee. It misses names, addresses, free-text PII and new token formats. I'd move it to the log pipeline (data classification at ingestion, field-level allow-lists for what the RCA tools may return), and keep the regex pass as defence in depth.

## Trusting the code it produces

5. **Proposed fixes are ordinary PRs.** The skill already only writes code after a high-confidence RCA, writes the failing test first, and never pushes. In production I'd go further. The branch becomes a draft PR with the incident report attached, it goes through the normal CODEOWNERS review and CI, and it is labelled as AI-proposed. The PR description says which claims the fix depends on, so the reviewer checks the reasoning as well as the diff. Nothing merges on the skill's say-so.
6. **Mitigation stays a human action.** I wouldn't add "execute rollback" even with approval prompts. A rollback proposal with exact command, evidence and success criteria gets you 90% of the time saving without the blast radius.

## Keeping it correct over time

7. **Ownership for the knowledge layers.** The taxonomy gets one owning team (SRE) and the overlay gets per-team owners. Overlay entries are reviewed like code, with an owner and a date, and expire unless re-confirmed. The skill only *suggests* overlay entries. An unreviewed overlay that says "this alert is always noise" is how a real incident gets dismissed.
8. **Feedback goes back into the evals.** Every report the on-call marks *wrong* becomes a regression scenario. Changes to SKILL.md, the taxonomy or the verifier run the full eval before merge, the same way code runs CI.
9. **A semantic verifier pass.** The deterministic verifier catches fabricated numbers, ids and non-existent queries. It does *not* catch a true number used to support a wrong conclusion, because inference claims are only checked structurally. I'd add an independent LLM check on inferences (does the cited evidence actually imply this?) and track how often it disagrees with the human label.

## Cost and load during incidents

10. **Rate limits on observability backends.** Twenty engineers in a SEV1 can each start an investigation; 40 queries × 20 against Prometheus/Datadog during an outage is real load. I'd add a shared budget per backend (not just per investigation), caching of identical queries across concurrent investigations, and a "one investigation per incident" convention, so the skill runs once and everyone reads the same report.
11. **Track cost and time per incident class.** Today a run is ~$0.5–1.3 and 1.5–3 minutes on fixtures. That is cheap next to an engineer-hour, but it should be monitored, and investigations that hit the budget should be flagged for review, not silently truncated.

## What I'd cut or keep

I'd keep the parts that turned out to carry the weight: read-only tools, query ids with an audit log, verifying the written report, and an eval that re-verifies independently instead of trusting the model's self-check. Most of the real failures I hit came from the boundaries between those parts, not from the model's reasoning: the verified draft that didn't match the shipped report, unreproducible relative windows, and context that changed mid-eval. That is where I'd keep investing.
