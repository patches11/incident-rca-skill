# What didn't work

Running log of things that failed, were wrong, or had to be redone — and what changed as a result.

1. **MCP SDK v2 API drift.** Planned on `mcp.server.fastmcp.FastMCP`; the installed SDK (2.3.0) renamed it to `mcp.server.mcpserver.MCPServer`. Small, but a reminder that AI-written scaffolding targets the API it remembers.
2. **Verifier accepted fabricated small numbers.** First version matched a quoted number against *any* number in the cited result. Timestamps (`2026-10-14T...`), version strings (`2026.10.14-1`) and ids (`q004`) meant almost any small integer "verified". Fixed by stripping timestamps/versions/ids before numeric matching; unit test `test_timestamps_do_not_satisfy_small_numbers` guards it.
3. **Verifier didn't detect a tampered audit result.** Re-run hash was compared with the *stored hash*, not the hash of the stored result, so editing the result in the audit log went unnoticed. Now all three must agree. Test: `test_tampered_audit_detected_on_rerun`.
4. **Docstring + string concatenation isn't a docstring.** `"""...""" + TIME_HELP` silently produced tool descriptions with no text (Python only treats a bare literal as `__doc__`). Caught by inspecting `tools/list`.
5. **Answer leakage via the report template.** The first template's example YAML was the pool-exhaustion answer (service, commit). Replaced with a neutral example.
6. **Eval failure: verified draft ≠ shipped report (novel-failure, empty overlay, run 1 of pass 1).** The skill drafted 15 claims with `values`, got 15/15 PASS from `verify_claims`, then — writing the report — compressed the claims into one-line flow-style YAML and dropped every `values` field. The eval's independent re-verification of the *report file* failed 15/15. Root cause: verification ran on an intermediate artifact. Fix (structural, not just wording): new `verify_report` server tool that reads `.rca/incident-report.md` itself; SKILL.md step 6 reordered to "write the file, then verify the file, edit, re-verify". The prompt rule "don't reformat claims" was added too, but the tool change is what makes it checkable. Lesson: verify the artifact that ships, never a copy of it.
7. **Eval runner counted a usage-limit outage as 21 skill failures.** The account hit its session limit mid-eval; every later `claude -p` exited in ~2s and was scored FAIL ("skill was not invoked"). Fixed: runs whose CLI result is an error / limit message are reported as ERROR and excluded from pass rates, with a count shown under the table. Results from that pass were discarded.
8. **I changed the environment during an eval, and the verifier caught it.** I edited `service-catalog.yaml` (adding `test_command`) while an eval was running. A bad-deploy run had cited the catalog (`q002`); when the eval re-verified, the re-run returned a different result and the claim failed. The verifier behaved correctly here. The lesson is about process: the org context is an input to the eval and has to be frozen while it runs. The runner should snapshot org-context into each workspace instead of pointing at the live directory (done below).
